# Feedback Bot — довідник системи (для Claude і для людини)

Telegram-бот зворотного зв'язку для персоналу ресторанів. Працівник надсилає
повідомлення про проблему (текст / голос / фото) → Claude класифікує →
керівники отримують сповіщення з кнопками статусу → задача зберігається в
Google Sheets. Є щоденний ранковий дайджест і ручний перелік невиконаних задач.

Увесь код — в одному файлі **[bot.py](bot.py)** (~2600 рядків), Python, бібліотека
`python-telegram-bot` (PTB) 22.7, `gspread`, `openai` (Whisper), `anthropic` (Claude).

---

## 1. Як запускається і перезапускається

- Запуск: `python -u C:\bots\feedback_bot\bot.py` (polling, не webhook).
- Процесом керує **UniversalBotWatchdog** — заплана­ована задача
  (`C:\bots\universal_watchdog.ps1`), що працює **як Адміністратор** і
  **автоматично перезапускає** бот через ~10с після падіння. Логи кожного
  запуску: `C:\bots\feedback_bot\logs\output_*.log` та `error_*.log`.
- **Перезапуск після правок** (потрібна ЕЛЕВОВАНА сесія, бо процес
  високоцілісний): у PowerShell «від імені адміністратора»:
  ```powershell
  Get-CimInstance Win32_Process -Filter "name='python.exe'" |
    Where-Object { $_.CommandLine -like '*feedback_bot*' } |
    ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
  ```
  Watchdog підніме новий код. Або `C:\bots\restart_all_bots.bat` (перезапускає
  ВСІ боти). Неелевована сесія отримає `Access denied`.
- Ознака, що піднявся новий код: у логу є рядок `post_init: transient user_data cleared`.

## 3. Що де зберігається

**Джерело правди — одна локальна база SQLite `feedback.db`** (модуль [storage.py](storage.py),
режим WAL, доступ серіалізовано RLock). У `bot.py` дані тримаються в in-memory
кешах (`user_profiles`, `msg_store`, `assign_store`, `chat_msgs_store`, `tasks_store`),
що завантажуються при старті й пишуться наскрізь (write-through) у БД.

Таблиці `feedback.db`:
| Таблиця | Що містить | Ключ |
|---|---|---|
| `profiles` | профілі (JSON) | telegram_id |
| `tasks` | **канонічний запис задачі** (статус, категорія, суть, заклад, лог, has_photo, seq) — джерело правди для дайджесту/переліку | fid (`T-0104-1`) |
| `msgstore` | кеш повідомлень `{ids:{uid:msg_id}, text, photo(file_id), photo_path}` (JSON) | fid |
| `assign` | кому доручено (JSON) | fid |
| `chat` | id повідомлень бота в кожному чаті для очищення (JSON) | chat_id |
| `shiftreports` | **підсумки змін** (рефлексивний відгук персоналу: `{telegram_id, business_day, text, sender_name, sender_role, restaurant, is_anonymous, source}`) — окремо від задач | `telegram_id:YYYY-MM-DD` |
| `meta` | службове | k |

- **Атомарність**: KV-таблиці пишуться транзакцією (`save_kv` = DELETE+INSERT, або `kv_put` per-key); `tasks` — upsert. Пошкодження неможливе.
- **Міграція**: при першому старті `storage.migrate_kv_if_empty` імпортує старі JSON
  (`user_profiles/message_store/assign_store/chat_msgs.json`), а `_post_init`
  одноразово імпортує задачі з Google Sheet у `tasks`. Старі JSON лишаються як бекап.
- `prompt.json` (промпт) і `bot_state.pkl` (PTB-persistence, `pending_photo`) — окремі файли (не в БД).

### Google Sheets — ДЗЕРКАЛО (аркуш «Зворотний зв'язок», 13 колонок)
`Номер | Дата | Час | Заклад | Хто повідомив | Роль | Категорія | Суть | Відповідальний | Терміновість | Фото | Статус | Лог`
- Бот **дублює** туди задачі/статуси/лог best-effort (`_mirror_*_to_sheet`, у фоні через `_arun`),
  але НЕ читає звідти для роботи — джерело правди це `tasks` у SQLite. Збій Sheets не впливає на бот.
- Задача ЗАКРИТА, якщо `status` ПОЧИНАЄТЬСЯ з `Виконано`/`Видалено` (`_is_resolved`).

## 4. Бізнес-процеси

### 4.1 Реєстрація
`/start` → ConversationHandler питає ім'я → прізвище → ДН → телефон → роль →
заклад → профіль зберігається зі статусом `pending` → адмінам летить заявка з
кнопками ✅/❌ (`handle_approve` / `handle_reject`). Статуси: `pending` → `active` / `fired`.

### 4.2 Надсилання повідомлення (головний потік)
1. Працівник шле текст / голос / фото (`receive_text` / `receive_voice` / `receive_photo`).
   - Голос → `transcribe_voice` (Whisper).
   - Фото може прийти першим (тримається 2 хв, `pending_photo`) або після кнопки «📷 Додати фото».
2. Показуються 3 кнопки: «👤 Відправити / 🕵️ Анонімно / 📷 Додати фото» + таймер
   автовідправки 20с (`ask_send_options` → `auto_send_callback`).
3. `_save_and_notify`: фото зберігається на `E:\` (+копія `G:\`, раз), для **кожної** підзадачі →
   `create_task` (запис у SQLite `tasks` + дзеркало в Sheets фоном, повертає `feedback_id`) → `send_notifications`.
4. `analyze_with_claude` може повернути **кілька** задач з одного повідомлення
   (масив JSON). Кожна — окрема задача й окреме сповіщення. Фото-`file_id`
   зберігається для всіх підзадач, але «живе» фото шлеться лише з першою.
5. `send_notifications` шле текст+кнопки кожному отримувачу (`get_recipients`),
   запам'ятовує `message_id` у `msgstore`, ставить таймер автовидалення 24год.

### 4.3 Кнопки статусу на сповіщенні (`handle_status_update`)
✅ Виконано · 🔧 В роботі · 👤/🔁 Доручити · 💬 Коментар · 🗑️ Видалити (лише власник).
- Редагує текст у ВСІХ отримувачів (`edit_all_messages`) + оновлює задачу в SQLite
  (`set_task_status` / `add_task_log`) + дзеркало в Sheets фоном.
- При «Виконано»/«Видалено» прибирає запис із `assign_store`.

### 4.4 Доручення (`handle_assign` → `handle_assign_to`)
Список активних співробітників → задача надсилається обраному окремим
повідомленням, у тексті задач з'являється «👤 Доручено: …». Доручений отримує
права на кнопки статусу цієї задачі.

### 4.5 Коментарі (`handle_comment` → `process_comment`)
Режим коментаря (2 хв), текст дописується в задачу (`add_task_log`) і дзеркалиться в `Лог` Sheets.

### 4.6 Ранковий дайджест (`send_unresolved_digest`, щодня 06:00 за часом сервера = ~09:00 Київ)
1. Видаляє попередні відстежені повідомлення бота у всіх отримувачів (`delete_tracked_messages`).
2. Шле «✅ Виконано вчора».
3. Бере невиконані задачі з **`tasks_store` (SQLite)**, сортує за `seq` (новіші згори),
   шле кожну окремо з кнопками (текст з `msgstore` або `build_row_text`, фото за `photo`/`photo_path`).

### 4.7 Ручний перелік (`show_unresolved`, кнопка «🔴 Невиконані завдання»)
Те саме, що дайджест, але читає `tasks_store` для одного адміна за запитом.

### 4.9 Підсумки змін (рефлексивний відгук персоналу)
Окремо від задач. Будь-який активний співробітник наприкінці зміни тисне reply-кнопку
**«📝 Підсумок зміни»** (або `/shift`) → 2-хв режим (`report_mode`) → наступний текст/голос
(Whisper) зберігається як звіт. Inline `🕵️ Анонімно` / `❌ Скасувати`.
- **Зберігання**: `save_shift_report` → таблиця `shiftreports` (ключ `telegram_id:день`, одна
  на людину/день; повторно того ж дня — ДОПИСУЄ). Анонімність прибирає ім'я/роль, лишає заклад.
  **Ніколи не пише в `tasks_store`/`msgstore`** — повна ізоляція від задач.
- **Менеджерам — БЕЗ пінгів на кожен звіт.** Раз/день у дайджесті (`send_shift_reports_section`,
  до раннього `return`) — ОДИН агрегований Claude-блок по закладах (`_summarize_shift_reports_sync`
  через `_arun`, кеш `_shift_summary_cache`, fallback-список без Claude). Тихий день — нічого.
  On-demand: «📝 Підсумки змін» в адмін-меню (`show_shift_reports`) — сводка + окремі звіти з
  кнопкою «➕ Створити задачу» (`handle_report_to_task` → `analyze_with_claude`/`_save_and_notify`).
- **Ескалація в задачу — лише вручну** (кнопка), ніколи автоматично.
- Ретенція `SHIFT_REPORTS_RETENTION_DAYS` (14 дн.), чистка `_purge_old_shift_reports` у дайджесті.
- М'який нудж «лиши підсумок» — один рядок у першому підтвердженні задачі за день (`_should_shift_nudge`,
  мітимо ПІСЛЯ успішної відправки). Опц. дзеркало в окрему вкладку Sheets — `SHIFT_REPORTS_TO_SHEET` (off).

### 4.8 Інше
- Привітання з ДН (`send_birthday_greetings`, 06:00).
- Адмін-меню (`show_admin_menu` / `handle_admin_menu`): список/очікують/зміна
  ролі/звільнити/відновити; для власника — перегляд і **редагування промпту голосом АБО текстом**
  (`process_prompt_voice`/`process_prompt_text` → `_apply_prompt_instruction` → `refine_prompt_with_claude`).
  У режимі `prompt_editing` будь-який текст власника = інструкція що змінити (reply-кнопки меню — перевіряються раніше).
- Зміна ролі співробітником (заявка) і адміном.

## 5. Ролі та права
- `RESTAURANTS = ["Терраса", "Хочу", "Хочу 2.0"]`
- `ADMIN_ROLES = {"Управляючий", "Виконавчий директор"}`
- `is_admin`: власник, або активний з ADMIN_ROLES.
- `can_manage_tasks`: власник + Управляючий + Виконавчий директор + Адміністратор (кнопки задач).
- `is_owner`: лише `OWNER_IDS` (видалення задач, промпт, призначення керівних ролей).
- **Reply-кнопка «👨‍💼 Адмін-меню» і саме меню** (`get_main_keyboard` / `build_admin_menu_keyboard`)
  показуються всім `can_manage_tasks`. Але вміст меню — за роллю: «Адміністратор» (can_manage_tasks,
  але НЕ is_admin) бачить лише «🔴 Невиконані завдання»; повні адміни — увесь набір; власник —
  додатково промпт. Дії меню гейтяться: персонал — лише `is_admin`, промпт/видалення — лише `is_owner`.
- **Маршрут за ЗАКЛАДОМ** (`get_recipients(category, restaurant)`): OWNER_IDS завжди;
  `RECIPIENT_ROLES` (Управляючий/Виконавчий директор/Адміністратор) — за їхнім набором закладів;
  Шеф-повар — кухонні категорії. Набір закладів рахує `_profile_venues(p)`: пріоритет — поле
  **`manages`** (список закладів, налаштовується в адмінці); інакше за роллю (Виконавчий директор/
  `all_restaurants` — усі; решта — `restaurant`). `visible_restaurants(uid)` — що в дайджесті/переліку;
  `can_act_on_task(uid, restaurant)` — права на кнопки/коментар/доручення. Безхазяйний заклад прикриває власник.
- **Адмінка → «🏠 Доступ до закладів»** (`menu_venues`, для `is_admin`): обрати керівника →
  `venueuser_{uid}` → тогли закладів `vtoggle_{uid}_{idx}` / «🌐 Усі» `vall_{uid}`. Пише `manages` у профіль
  (write-through `save_profiles`). Один / кілька / усі заклади per-користувач.

## 6. Життєвий цикл повідомлень у чаті
Сервісні повідомлення автовидаляються (30с звичайні / 120с меню / 24год задачі).
Усі повідомлення бота трекаються (`track_msg`) і витираються перед дайджестом/переліком,
після чого актуальні задачі надсилаються наново.

## 7. ПРАВИЛА для майбутніх правок (важливо!)

Систему зроблено стійкою до втрати фото/повідомлень. Щоб НЕ зламати це:

1. **Ніколи не клич `bot.send_message` / `edit_message_text` / `send_photo` напряму.**
   Використовуй `safe_send_message`, `safe_edit_message`, `safe_send_photo` — вони
   повторюють відправку звичайним текстом при помилці Markdown і обробляють
   flood-control/мережу. Інакше повідомлення можуть тихо зникати.
2. **Будь-який динамічний текст** (ім'я, summary, коментар) у `parse_mode="Markdown"`
   ОБОВ'ЯЗКОВО проганяй через `md()` (= `escape_markdown(version=1)`).
3. **Створення `Bot`** — лише через `get_bot()` (один спільний екземпляр), не `Bot(token=...)`.
4. **Дані** — лише через `storage` (SQLite). Профілі/msg_store/assign/chat: in-memory кеш +
   `save_*` (write-through `storage.save_kv`/`kv_put`). Задачі: `create_task` / `set_task_status`
   / `add_task_log` (пишуть `tasks_store` + SQLite + дзеркало Sheets). Не пиши JSON-файли руками.
5. **Будь-який виклик gspread або Claude** — синхронний і блокуючий → загортай у
   `await _arun(lambda: _sheet_retry(fn))` (для таблиці) або `await _arun(...)` (Claude).
   Ніколи не клич gspread/Claude напряму в async-хендлері — заблокуєш бот.
   Дзеркало в Sheets — лише через `_mirror_*_to_sheet` (best-effort, фоном).
6. Джерело правди для задач — **`tasks_store` (SQLite)**, НЕ Google Sheets. Дайджест/перелік
   читають `tasks_store`. Sheets — одностороннє дзеркало; її недоступність не впливає на бот.
7. `msgstore` — лише кеш (id повідомлень + готовий текст + фото). Якщо БД задач недоступна,
   `create_task` усе одно дасть id (БД локальна, практично завжди доступна).
8. Фільтр «закрита задача» — `_is_resolved` (startswith), не підрядок.
9. Кнопки/`callback_data`: `feedback_id` ↔ `safe_id` через заміну `-`↔`_` (перші 2 рази).
   Будь-який новий хендлер, що міняє стан, мусить перевіряти права (`is_admin`/`is_owner`).
10. Після правок — `python -m py_compile bot.py storage.py`, тест імпорту (з ТИМЧАСОВОЮ
    `storage.DB_PATH`, щоб не створити реальну `feedback.db` передчасно), і перезапуск (розділ 1).
11. **Reply-клавіатуру (`get_main_keyboard`) НІКОЛИ не вішай на повідомлення, яке потім
    автовидаляється (`schedule_delete`).** У Telegram reply-клавіатура «прив'язана» до останнього
    повідомлення-носія; видалення носія прибирає кнопки (зокрема «Адмін-меню»), і відкату на
    старіший носій НЕ відбувається. Клавіатура має жити на ПОСТІЙНИХ повідомленнях: `/start`,
    привітання при відновленні/підтвердженні, перші повідомлення дайджесту/переліку. Підтвердження
    надсилання (ефемерне) клавіатуру НЕ несе.

## 7.1 Поведінка після аудиту (2026-06): сигнал > шум, контроль виконання
- **Терміновість керує реалтаймом**: `REALTIME_URGENCY = {Висока, Стандартна}` пінгуються одразу
  (за закладом); **Низька** — створюється тихо, лише в ранковому зведенні. Іконка терміновості 🔥/🟢.
- **Петля з відправником**: при створенні зберігаємо `reporter_id` (None для анонімних). При «Виконано»/
  «Видалено» — ОДНЕ повідомлення автору (`_notify_reporter`, не пінгує самого виконавця).
- **Вік/SLA/ескалація**: задача має `created_ts`, `acknowledged_at` (ставиться при «В роботі»),
  `completed_date` (при закритті), `escalated`. `sla_sweep` (кожні 30хв): (1) дослати недоставлену
  термінову; (2) прострочену термінову (`SLA_HOURS`) без реакції — раз ескалювати власнику. У переліку
  показуємо вік `⏰Nд` і `⚠️без власника`; сорт за терміновістю+віком.
- **Ідемпотентність статусу**: 🔄 не «перевідкриває» вже закриту задачу.
- **Дайджест/перелік — персонально за закладом** (кожен бачить лише свої заклади; групування `🏠 Заклад`),
  «Виконано вчора» — за `completed_date`.
- **Дублі**: атомарне «захоплення» `pending_message` у process/_do_process; вхід у коментар/доручення
  скасовує незавершену автовідправку; голос у режимі коментаря не створює задачу.

## 8. Бекап і відомі обмеження
- **Бекап БД** (3-2-1): `daily_backup` (05:30) → `VACUUM INTO` у `BACKUP_DIRS` (E: і G:), ротація
  `BACKUP_RETENTION`, перевірка `integrity_ok`. WAL зливається в основний файл: `checkpoint_job`
  (кожні 10хв) + `storage.close()` при зупинці. **Відновлення = взяти останній `feedback_YYYYMMDD.db`**,
  НЕ видаляти живу базу (старі JSON застарілі, з них тасків нема).
- `job_queue` НЕ персиститься — короткі таймери гинуть при рестарті; `sla_sweep`/дайджест self-heal.
- Старі JSON — лише для першої міграції, НЕ актуальний бекап.
- `feedback.db` (+`-wal`,`-shm`) — у `.gitignore`.

## 9. Git / безпека
- Remote: `origin` → `github.com/aceclub3/staff-manager-bot`, гілка `master`.
- `.env`, усі `*.json` (стори + службовий ключ), `bot_state.pkl`, `*.bak`, `logs/`,
  бекапи — **в .gitignore**, у репозиторій не потрапляють.
- `git commit` + `git push` робити одразу після завершення правки, БЕЗ запиту дозволу
  (правило власника, встановлено 2026-05-31). Комітити лише власні зміни (точково `git add`
  потрібних файлів), не чіпаючи сторонні видалення/нетрековані файли в робочому дереві.
